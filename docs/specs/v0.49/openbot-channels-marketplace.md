# OpenBot study: channels, marketplace, skills, multi-agent, providers (notes for SeraBot v0.49)

Source studied (read-only, untrusted data): the `openbot` clone in the session scratchpad. Nothing was run or installed.
Paths below are relative to that clone. No secrets copied. OpenBot defines no Claude OAuth client ID itself (it delegates to the CLI). The GitHub App public client ID is read from `app.clientId` in `src/main/github-connector-service.ts` (do not copy it; SeraBot needs its own GitHub App).

Key architectural fact: OpenBot is an Electron/TypeScript app that **wraps vendor CLIs** (Claude, Codex, Antigravity `agy acp`, OpenCode, Hermes, Kimi, Copilot, Cursor, Cline, Muse...) over ACP/JSON-RPC and lets each CLI own its OAuth. It does not implement Claude or Google OAuth natively. So for "native" sign-in the useful parts to copy are: per-account state folders, credential-file layout, refresh-hazard handling, pool/failover logic, error classification. The OAuth URLs themselves must come from SeraBot's own Antigravity/HielCowork implementation (user instruction: antigravity follows HielCowork).

## 1. Channels and messaging (Slack, Discord, Telegram, WhatsApp)

Docs: `docs/architecture/channels-and-messaging.md` ("Messaging connections"), `docs/messaging.md`. Code: `src/backend/messaging/` (platform-agnostic `MessagingThreads`), `src/main` (`MessagingService`, one `MessagingDriver` per platform = adapter + transport), seam `messaging-types.ts`. Storage: `projection_messaging_connections`, `projection_messaging_threads`, `projection_messaging_memories`, `projection_messaging_allowed_senders`, `projection_messaging_history`, `projection_messaging_pings`.

Design pattern common to all platforms:
- One **orchestrator agent per platform** (Slack/Discord/Telegram Orchestrator) receives each new conversation, answers short requests, delegates to one teammate with `send_message`; the answer returns as a follow-up turn in the same external thread (`messagingReturn` origin).
- Each external conversation = a link row + its **own execution thread** (side thread), hidden from public chat. Reply chain/thread id is the conversation key.
- Inbound message is a mailbox message from `user` with a `messaging` origin; idempotency key dedupes redeliveries (in-memory set + mailbox key survives restart).
- Output UX: eyes reaction on arrival, "Working on it..." status post with Stop button, replaced by the answer; check/cross/stop reaction at end; a `NO_REPLY` sentinel lets the agent stay silent. Posts never ping channel/@here/@everyone/roles; only explicit user mentions.
- Approvals posted in-thread with Approve/Deny; only the user whose message started the turn may answer (host can always answer). Button value = random in-memory token.
- External text is framed as untrusted input in the prompt; earlier thread messages and connection "facts" (memories) rebuilt each turn.
- Order: one turn per agent; external requests queue behind the agent's own work.

### Slack
- Single shared Slack app (`apps/slack-app/production/manifest.json`). Bot scopes: `app_mentions:read, channels:history, channels:join, channels:read, chat:write, files:read, files:write, groups:history, groups:read, im:history, im:read, im:write, mpim:history, reactions:write, users:read`. Bot events: `app_mention, channel_created, message.channels, message.groups, message.im, message.mpim, app_uninstalled, tokens_revoked`. Interactivity on, same request URL.
- Install: desktop calls `POST /v2/slack/authorize` -> Slack install URL; a central Worker exchanges the code at `/v2/slack/callback` (client secret lives only there), links the workspace to the host in D1 (`slack_workspace_routes`: team, host, account; no token) and returns the bot token **sealed to a one-use host key** (`@openbot/contracts/slack-workspace-grant`) via the `openbot://slack-workspace` deep link.
- Events: Slack -> `https://signal.openbot.run/v1/slack/events` (central "Signal" service verifies Slack signature, answers `url_verification`, reads only app id + workspace id) -> forwards the exact body over a WebSocket "ingress" to the host holding a route ticket (ES256 JWT, 5 min, lists linked workspaces; revocation via signed auth-event outbox). Host must answer within 2.5 s or Signal returns 503 so Slack retries. Slack disables events if >95% fail for 60 min (offline hosts are a risk).
- Joins all public channels on start and on `channel_created` (`conversations.list/join`); private channels need `/invite`.
- Disconnect: revoke token, unlink workspace, delete orchestrator if last.
- Takeaway for SeraBot (no central relay, <=10 users, one binary): skip Signal/D1/route tickets. Use Slack **Socket Mode** (app-level token, outbound WS) so no public endpoint is required, or an API route with signature verification (HMAC-SHA256 over `v0:{ts}:{body}`, reject >5 min skew).

### Discord
- One shared app (`apps/discord-app/README.md`), scope `bot`, **no privileged intents** (guilds, guild messages, DMs only). Signal holds the Gateway (`@discordjs/ws`) and REST (`@discordjs/rest`); hosts never get the bot token. Only guild messages that mention the bot or its auto-created bot role, and button presses, are forwarded.
- Conversation = reply chain keyed by first message; every bot post replies to it; replies must keep the mention (Discord "@ ON"). DM -> one fixed line "mention me in a server channel".
- Context on new conversation: last 10 messages from the prior 15 min; without Message Content intent only mention messages carry text/files.
- Limits: 2000 chars per post (split), 10 MB file cap; new text posts allow only user mentions.
- Per-guild "Who can use OpenBot" = allowed role list (empty = everyone). Bot removal detection: unlink on guild leave plus periodic reconcile (30 min) that never runs while a shard is closed.
- Takeaway: with a few users, run the Gateway inside the Rust binary (`serenity` / `twilight-gateway`), mention-only, no privileged intents, per-guild role allowlist.

### Telegram
- One central bot, token only in Signal (`TELEGRAM_BOT_TOKENS`). Link flow: host asks `POST /v2/remote/hosts/<id>/telegram-link` for a one-use code (15 min), opens `t.me/<bot>?startgroup=<code>` or `?start=<code>`; Telegram sends `/start <code>`; chat is linked to that host (stores hashes only). Host creates the connection only on the `linked: true` flag (anyone in a routed chat can type /start with a bogus code).
- Webhook `.../v1/telegram/updates/<botId>` with per-bot secret header; always answers 200. Supergroup: each reply chain = conversation (`message_thread_id`); forum topic = conversation; DM = one; basic group uses an in-memory reply map. Mention starts, reply continues. No history API, so chat state (names/last messages) kept in memory.
- File helpers: signed one-use tokens for `getFile`/`sendDocument` (20 MB).
- Takeaway: SeraBot already has `crates/serabot/src/telegram.rs` with per-user links; extend with the same conversation-key rules (thread id / reply chain) and the orchestrator pattern. Keep invitation-only: link code bound to the acting user id.

### WhatsApp
- Runs as a **linked device of the host** (no central service): `packages/whatsapp` vendors Baileys v7.0.0-rc14 (MIT) minus copyleft parts, with clean-room Signal code (`src/signal/`).
- Store: `WhatsAppAuthStore` = one SQLite file per number in `<userData>/whatsapp/`, every value AES-256-GCM sealed with a random key held by the credential store (`whatsappStoreKey`), exclusive locking so a 2nd process cannot take the session; plus last day of posts (retry receipts), journal of received messages (30 min), reply chains (7 d).
- Session: no history sync, not online on connect; close codes: 401/403/411 -> `invalid_token` (relink), 440 -> `error` (another client has it), 515 restart now, others backoff 2-30 s with jitter; 90 s silence watchdog; posts wait up to 5 min for the socket, >=1 s between posts per chat, message id allocated before send (so own echo is not read as a request).
- Link: QR or phone pairing code; the page polls state ~1 s.
- Sender policy (`whatsapp-senders.ts`): owner's self-chat always counts; on the owner's personal number nobody else counts unless allow-listed and OpenBot never writes first; on a bot-only number an unknown DM sender gets one pairing code (max 3 pending, 1 h); groups only when allowed. Approvals are numbered text answers (`1`, `2`). "Quiet end": on a personal number a failure posts nothing in another person's chat (it would look like the owner wrote it).
- Saved history (none is synced): messages of allowed chats stored in `projection_messaging_history`, files <=2 GB per connection, 90-day retention, deletes/edits honored only from the saved author id.
- Takeaway for Rust: no Rust equivalent of Baileys with equal maturity is vetted. Safer v0.49 options: (a) WhatsApp Cloud API (Meta webhooks + `X-Hub-Signature-256` HMAC, needs a business number) or (b) defer WhatsApp and document it. If a linked-device client is adopted later, copy the sender policy, quiet-end rule, sealed per-number store and close-code table.

### Notification/attention model (for the chat UI work)
`docs/architecture/channels-and-messaging.md` (top half): events that notify (finish, error, waiting for input/approval/browser step), per-agent/server levels (`all`, `needs-me`), previews with secret redaction, events held 5 min and suppressed when the user is active elsewhere (30 s idle window), side-thread notification opt-in. Good model for SeraBot's attention/badge logic.

## 2. Shared channels and multi-agent orchestration inside OpenBot

Source: `docs/architecture/channels-and-messaging.md` ("Shared channel chats"), `docs/architecture/agents.md` ("Agent threads", "Agent communication policy").

- **Channel** = host, purpose, agents (members), selected lead, linked execution threads (one thread per channel-agent pair, never the agent's normal thread). Canonical transcript, tasks, assignments, summaries in SQLite (`ChannelStore`), rebuildable from events; commands carry operation ids and receipts (idempotent retries).
- **Routing** (`ChannelService`): deterministic first (explicit recipient, reply-to task, `@mention` list, `@everyone`, typed names, sole open task, single member), no model; else the **lead** model routes with a schema-constrained answer and no tools. Invalid routing never broadcasts; a mentioned member is never idle.
- **Member tools**: `channel_assign` (child task), `channel_transfer`, `channel_result`, `channel_history`, `channel_reply` (member-to-member, max 2 per request, caller waits), `channel_cancel`, `channel_add_member/remove_member/set_instructions`, routine tools; `create_channel/update_channel/list_channels/send_to_channel` from an agent's own chat. Person-request guard: management tools refuse when the request author is a routine/agent (prompt-injection defense).
- **Limits**: 8 automatic assignments per root request, 2 active assignments per channel (`CHANNEL_PARALLEL_LIMIT`), one channel turn per agent at a time; declared resources `browser` and `workspace:<path>` are serialized.
- **Context packet**: budget 120,000 chars, transcript share 1/4 newest first, background summary at 0.75 of threshold using a cheaper model (`backgroundModel`), provider compaction at 80% of window, stop after 2 ineffective/failed compactions, `channel_history` page 24,000 chars. Task revisions stop a stale assignment completing a corrected request.
- **Stop/Cancel/Continue/Reassign**: stop pauses a task and descendants; cancel ends the whole run; "continue" resumes stopped tasks; restart recovery checks accepted provider work and flags unknown outcomes (no exactly-once for external effects).
- **Agent side threads (tasks)**: `projection_agent_threads`; each side thread has its own lane/queue/provider thread. Per-agent `taskLimit` (1..4, default 4), host cap 64; server-wide `TurnSlots` (priority: person messages first, then routines/teammates, oldest first; no slot ever waits on another slot). Hold reasons: `task-limit, agent-restarting, usage-limit, server-busy, agent-busy, one-turn`. Providers with `concurrentTurns:false` get 1.
- **Teammate delegation**: `openbot.list_agents` (status, queuedMessages, turnStartedAt, lastActivityAt), `read_agent`, `send_message` (answers come back as new deliveries), `interrupt_agent` (cannot stop work started by user/routine/another agent), blocked reply format `Status/Result/Evidence/Unblock`. Multi-recipient answers wait until the last copy ends, then run in one turn. A turn of teammate results that ends empty fails with cause `empty_answer` (avoids silent team stalls).
- **Subagents inside a CLI turn**: provider notification `turn/subagents/updated` carries the full subagent list of a turn (`src/backend/agent/subagent-updates.ts`, `acp-subagent-updates.ts`); steps bounded (`CONVERSATION_SUBAGENT_STEP_LIMIT`), tool calls map to step kinds (read/search/edit/command/web/tool). OpenCode background subagent/shell results arrive in separate turns with no updates, recovered via flavor flag `unsentBackgroundTurns`.

### Bot-manages-bots (user request: main bot edits providers, models, thinking)
- `update_profile` and `update_agents` tools (`src/backend/agent/profile-tools.ts`, `update-agents-tool.ts`, `model-tools.ts`): fields `provider`, `model` (ids from `list_models`), `reasoningEffort`, `providerAccountId` (null = provider's own sign-in / pool), `backupModels[]` (<= `AGENT_BACKUP_MODEL_LIMIT` = 8, each `{provider, model, providerAccountId?}`), `automatic` flag for failover. A runtime change during a turn is stored as `pendingRuntime` and applied before the next turn. `update_agents` applies the same settings to many agents in order; a failure for one does not stop the rest and the result names it. `widensAgentSettings` gates privilege widening (access, computer use). `list_models` filters by provider/query.
- Reasoning efforts (`packages/contracts/src/ipc-agent-identity.ts`): `none, minimal, low, medium, high, xhigh, max, ultra`; released peers know only `low..max`, and `legacyReasoningEffort()` maps none/minimal -> low, ultra -> max. Each model lists its own supported efforts + default. Claude: discovered `supportedEffortLevels` among `low, medium, high, xhigh, max`, default `high` if supported else first (`claude-client.ts` ~L1110-1140), applied live with `applyFlagSettings({effortLevel})`. ACP agents publish a `thought_level` config option per model, probed one model at a time with a 5 s total budget and 1 s per model (`acp-configuration.ts`); a model with no effort option is `reasoningEffortConfigurable:false` and nothing is sent. When a catalog drops a model, `moveAgentsOffUnlistedModels` migrates to the newest model of the same family, preserving the effort variant named in the id (`-high`, `-thinking`).

## 3. Fallback models and failover (`docs/architecture/providers.md` "Backup models and failover")

- Ordered `AgentBackupModels` (max 8) in `agent_json`; automatic or ask-in-chat.
- Two triggers handled by `UsageLimitGate` + `AgentService.#usageLimitMove`:
  1. **Plan usage limit**: holds the queue of every agent on that provider-account+model until reset; the agent moves to the first ready backup not held. `usageLimitReturn` remembers the original model and returns when the hold ends. A user-picked model drops the return.
  2. **Provider error** classified by `classifyFailure`: `billing, provider_unavailable, rate_limit, authentication, network, timeout`. If the turn did no work yet (`!acted`) and a ready backup exists: messages go back to the queue, the failed model is passed over for **10 minutes**, the next drain runs the turn on the backup with no error banner; the hold also ends when a turn on the model completes; restart clears holds. Notes: `model-switch:provider-error`, `...-ended`.
- A turn that already wrote text or ran a tool fails normally (no blind replay of possible side effects). Tasks, channel tasks, a refused `turn/start`, and a provider failing to start do not fail over. A message reruns at most once per failed model.
- Channel tasks: when an agent owning waiting channel work hits its usage limit it moves to its backup; a marker shows in chat and in each affected channel.
- Usage read pacing (`usage-read-gate.ts`): one read at a time, 4 min cache, failure backoff 5/10/20/40 min up to 1 h, reset on credential change/sign-out (Claude's usage endpoint answers 429 for an hour if hammered).
- `provider-diagnostics.ts` + per-flavor regexes classify provider text. Antigravity: `RESOURCE_EXHAUSTED`, `MODEL_CAPACITY_EXHAUSTED`, "quota ... reached" (resets in days), 429, 50x, `User location is not supported`, `VALIDATION_REQUIRED` carrying an `accounts.google.com/signin/...auth_success_gemini` link. Copy these categories into SeraBot's classifier and keep three outcomes distinct: wait, switch model, user must act (verify account).

## 4. Provider accounts, sign-in and multi-account

### Claude (account model)
- Sign-in kinds (`src/backend/provider-drivers.ts`, `id:"claude"`): browser: `claude auth login --claudeai` (CLI opens the page and takes its own loopback callback; on Windows OpenBot opens the page itself, `windowsPageByOpenBot`, because `rundll32` can hang); remote/no browser: same command under `script` (util-linux) giving a link and a "Paste code here" prompt (`flow:"paste"`, `agent/cli-code-login.ts`); sign-out `claude auth logout`.
- **Multi-account = one config folder per account**: driver `accounts.homeVariable = "CLAUDE_CONFIG_DIR"`; accounts after the first live in their own folder and every process (sign-in, status, agent) is started with that variable. `MAX_PROVIDER_ACCOUNTS = 10` (`packages/contracts/src/ipc-agent-status.ts`). The key account is a virtual account with fixed id `CLAUDE_API_KEY_ACCOUNT_ID` whose agents get `ANTHROPIC_API_KEY`; the provider's own sign-in uses the saved key only when it has no claude.ai account. Store: `agent/provider-account-store.ts`, logic `agent/provider-accounts.ts`; folders removed after a best-effort sign-out.
- Stored credential layout (`claude-stored-sign-in.ts`, read without starting the CLI): `<configDir>/.credentials.json` -> `{"claudeAiOauth":{"refreshToken","refreshTokenExpiresAt?","subscriptionType?"}}`; macOS Keychain generic password service `Claude Code-credentials` (suffix `-<sha256(configDir)[0..8]>` for custom dirs); account metadata (email, organizationUuid/Name) in `.config.json` or `<CLAUDE_CONFIG_DIR|~>/.claude.json` under `oauthAccount`. Env variables that bypass the store: `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_OAUTH_REFRESH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY/...`.
- **Refresh hazard to copy**: `claude auth status` may start an OAuth refresh near expiry and exit after 2 s without saving the rotated tokens; the next process then gets `invalid_grant` and the user is signed out (anthropics/claude-code#95822, #105645). OpenBot therefore reads the stored credential (refresh token present = signed in) and lets only the agent process refresh. Rule for SeraBot: one writer of the refresh token per account (serialize refresh with a per-account lock; persist rotated tokens atomically before using the new access token).
- Account pool (`agent/provider-account-pool.ts`): among accounts that keep a buffer, pick the one whose **longest window resets first** (short window <=24 h keeps 15% free, longer 5%, unknown 10%); stay on the current account unless another reset differs by >10 min; accounts without a reading rank after those with one; if none has buffer, choose the most capacity left. A named account stays until its limit; `providerAccountId=null` hands the agent to the pool.

### Codex (reference for device flow)
- `agent/codex-login.ts`: app-server `account/login/start` returns `authUrl`; Codex takes the loopback callback (port 1455 in current releases); remote: `codex-device` device code. Per-account `CODEX_HOME`.

### Antigravity / Gemini (`agy acp`)
- Runs `agy acp` (Antigravity CLI 1.5.x) over ACP. Sign-in = ACP `authenticate` with `methodId: "oauth-personal"` (Google account, Google AI Pro/Ultra plans) or `"gemini-api-key"` (saved key injected as `GEMINI_API_KEY`; the saved key wins over a Google account; accounts after the first never get the key). `startAcpAuthentication` (`acp-sign-in.ts`) runs the call in its own process (the server opens the browser and blocks until done); on non-Windows OpenBot puts its own `open/xdg-open` shim first on `PATH` to capture the Google URL; with `logout:true` it first calls ACP `logout` so Reconnect is a real new sign-in.
- **Multi-account**: per-account `GEMINI_HOME` folder passed as CLI flags `--gemini-dir=<home>` and `--app-data-dir=antigravity-acp` (the CLI ignores the env var). On macOS the CLI would share one Keychain item, so OpenBot sets `WSL_DISTRO_NAME=OpenBot` to force the file store `antigravity-oauth-token` inside the app data dir on every platform (`provider-drivers.ts` ~L345-370).
- Token file (`antigravity-token-import.ts`): `{"token":{"access_token","token_type":"Bearer","refresh_token","expiry"},"auth_method":"consumer","id_token_email":""}` mode 0600; the legacy 1.4 `acp_token.json {refresh_token}` is copied once with an `openbot-token-imported` marker and `cache/acp-auth-state.json {methodId:"oauth-personal"}`. The marker prevents resurrecting a signed-out account.
- Quota (`antigravity-usage.ts`): with the access token from the file (valid, unexpired), `POST https://cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` -> `cloudaicompanionProject`, then `POST https://daily-cloudcode-pa.googleapis.com/v1internal:retrieveUserQuotaSummary {project}`; groups with `buckets[{window,displayName,resetTime,remainingFraction}]`; a group description "Models within this group: a, b" maps models to buckets; the "Gemini models" group is preferred. Headers: Bearer, JSON, an Antigravity-style `User-Agent`. Every failure = no reading (never an error). 2 endpoints are overridable for tests via an env var.
- Behavior flags (`acp-flavor-antigravity.ts`): disable tools `schedule` and `run_workflow` via `sessionMeta`; failures arrive as answer text starting with a warning sign or `Agent execution error:` and end the turn as success, so they are regex-matched and converted to failures; a "Usage Limit Reached" chunk -> usage_limit cause (stop reason `refusal`); cancel is local then `session/resume`; `closeKeepsSession` (a ~100 MB harness leaks per session until process exit) -> one process per session; steering by sending another prompt since 1.5.0; the model list is best-first (do not re-sort); `authRequired` from a refused refresh -> mark signed out. Antigravity 1.4 offered Claude/GPT models only to a client named `zed`; 1.5 offers them to all.
- Sign-out: ACP `logout`; a terminal CLI keeps its own sign-in because the token file is OpenBot's.

### OpenCode (user: "for opencode, claude see how openbot does it")
- `opencode acp`; **no login OpenBot can drive**: the account is one key. The stored key (envelope-encrypted, `src/main/provider-credential-store.ts`, only a status crosses IPC) is injected only as `options.apiKey` of provider `opencode-go` inside `OPENCODE_CONFIG_CONTENT`, never as `OPENCODE_API_KEY` or on the free `opencode` provider (a key on the free provider made every free model fail with "provider authentication required", #7550). `OPENCODE_DISABLE_AUTOUPDATE=1`.
- Signed-in state is derived from the models `session/new` returns, not from a credential; keyless = `available` with free models only.
- Agent defaults (`opencode-agent-defaults.ts`): deny `question`, MCP resource tools, `report`/`opencode` skills via an `OPENCODE_CONFIG` file in the provider state dir (not `_CONTENT`, so project config wins; skip rules the user's global config matches) -> about 12% fewer prompt tokens.
- MCP: OpenBot starts each stdio server itself (`mcp-stdio-relay.ts`) and gives OpenCode a loopback Streamable-HTTP URL + bearer; sessions in one directory share the relay. (SeraBot does not run stdio plugins, so not applicable.)
- Catalog: free models first (`opencodeModelRank`, `OPENCODE_RECOMMENDED_FREE_MODELS`, `isFreeOpencodeModel` = name ends "Free" or id in an explicit list), relist 5 s after start (the first list is cached/partial), usage via `GET opencode.ai/zen/go/v1/usage` with the same key. Steering via ext method `_session/steering` (capability in initialize `_meta.steering.supported`). Error mapping: -32000 "provider authentication required" -> name the provider from the model id prefix.

### Hermes
- `hermes acp`, user-installed (pinned installer script with SHA-256 check). Sign-in `hermes auth add nous --type oauth` (Nous Portal device code); stdin closed so the "import shared credentials" prompt answers yes; parse the `Open:` URL, not `Portal:`; watch `auth.json` mtime to detect an external sign-in. Models are `provider:model` ids grouped by provider. Settings merged via `HERMES_MANAGED_DIR` only for keys the user lacks (`coding_context: focus`, `disabled_toolsets:[browser]`, about -16% prompt tokens). Quirk: use `session/load`; a null reply = missing session.

### Muse / Muse Code (`muse-client.ts`, `muse-protocol.ts`, `agent/muse-login.ts`)
- `@muse-code/sdk` (`muse serve` over MSP), pinned 1.4.2. Device sign-in: spawn `muse serve --disable-shell --disable-write`, strip `META_API_KEY` from env, `initialize` with `experimentalApi:true`, start login -> `{verificationUrl,userCode}`, then wait for `{outcome}`; cancel with `account/loginCancel` on scope close. Account check via experimental `account/read` on a short-lived host; a CLI without it = "not verified" but keeps running. Explicit Meta API key allowed (encrypted store). Profile generation with Muse is refused (the pinned host cannot be tool-free).

### Others worth borrowing
- Kimi: `kimi login --json` device-code JSON lines, `BROWSER=true` on non-Windows, usage `GET <base_url>/usages` with the CLI token (5 h / weekly / monthly windows, `https` only), token lasts 15 min and is only refreshed by the CLI during a turn.
- Copilot: `copilot login` (loopback) or `--device-code`; token precedence `COPILOT_GITHUB_TOKEN` > `GH_TOKEN` > `GITHUB_TOKEN` > keychain; sign-out via ACP `logout`.
- Cline: ACP `authenticate` with `cline`; `CLINE_API_KEY` env; free models list in `cline-free-models.ts`. Cursor: `link` flow. Grok: device flow with `GROK_OAUTH2_REFERRER=openbot`.
- Remote sign-in relay (`docs/architecture/integrations.md` "Remote sign-in: the callback relay"): the host captures the provider page, a remote client opens it and replays the loopback callback query to the host's listener. Kinds table: loopback, device code, pasted code, CLI-owned browser, deep link, terminal, key. A CLI that opens its own browser and honors no `BROWSER` cannot be relayed; give it a device/paste flow.
- Add-a-provider checklist (`integrations.md` "Add a provider"): descriptor row (`displayName, authKind, signInMessage, skillFolders`), driver row (signIn + codeSignIn + accounts), CLI resolver, state paths for confinement, error keys, logo.

## 5. Marketplace, connectors and skills

### Plugin catalog (`marketplace/plugin-catalog/`, `docs/plugin-distribution.md`, `docs/architecture/skills-and-plugins.md`)
- 253 plugins as `plugins/<slug>/plugin.json` plus `catalog.json {schemaVersion, catalogVersion, updatedAt, order[]}` (featured order first). Shape: `slug, name, tagline, description, category, creatorName, iconUrl, version, prompts[{id,text}], apps[{id,name,description,iconUrl,server{...}}], skills[], websiteUrl, privacyPolicyUrl, termsUrl`.
- `server.transport`: `http` (246) or `stdio` (7). `server.auth[]` kinds: `link` (228, browser OAuth via MCP OAuth), `key` (12: `fields[{id,label,env,hint}]`, `docsUrl`), `local` (1, e.g. Figma desktop server at `http://127.0.0.1:3845/mcp` with `steps[]`).
- Examples: Canva = `http` `https://mcp.canva.com/mcp`, auth `link` (each user signs in; the agent acts as that account; prompts: recent design, resize+export, deck from notes); GitLab = `https://gitlab.com/api/v4/mcp`, `link`; Brave Search = `stdio` `npx -y @brave/brave-search-mcp-server` with a `key` field env `BRAVE_API_KEY`. Catalog also has figma, linear, notion, stripe, atlassian, sentry, vercel, supabase, neon, cloudflare, airtable, clerk, etc. There is **no `github` catalog plugin**: GitHub is a first-class *connector* (below).
- Install = save the app as a host-global MCP server + install pinned skills into the chosen agent; share links `openbot.run/plugins/<slug>` / `openbot://plugins/<slug>`; catalog cached in the user-data dir (static files, no account needed).
- **MCP OAuth** (`src/backend/mcp-oauth-provider.ts`, `integrations.md` "How an MCP sign-in renews and ends"): loopback redirect on 127.0.0.1:28417 path `/mcp-auth` (fallback `openbot://mcp-auth`); uses the MCP SDK dynamic client registration + PKCE; renewal via `refreshAuthorization` (never re-registers). Token endpoint outcomes: new tokens = replace; `invalid_grant` = drop tokens, keep client registration, mark sign-in needed; `invalid_client/unauthorized_client` = drop tokens and registration; network/5xx/timeout = keep everything. Revocation: best-effort RFC 7009 per token (refresh first) with a 5 s limit. `secureOAuthFetch`: body <=1 MiB, answer <=20 s, every OAuth endpoint must resolve to public IPs when the MCP host is public. Checked by `bun run test:mcp-oauth`.
- **Multi-account per MCP server**: each account = one http row; address gets a `#account-<id>` fragment (never sent on the wire); OAuth record keyed by address+fragment; the message tags the account with `@<row name>`; the first account keeps the listing URL.
- **Agents never see OAuth tokens** (`src/backend/mcp-oauth-proxy.ts`): loopback proxy `http://127.0.0.1:<port>/mcp/<route>/<agent>`; route = digest(row id + URL); bearer = HMAC(route+agent, proxy secret) compared with `timingSafeEqual`; 403 for wrong Host/path/bearer; injects the current token upstream, drops provider Authorization/cookies, follows only same-origin 307/308 (<=3), on upstream 401 does one refresh + retry, with no sign-in returns JSON-RPC `-32001` (never 401, so the provider will not start its own flow); rewrites `clientInfo` to `{name:"openbot", title:"<agent> (OpenBot)"}`; port + secret persisted encrypted so resumed sessions keep working. This maps onto SeraBot's `plugin_runtime.rs` (HTTPS, pinned IP, approval-gated) and `mcp_client.rs`.

### GitHub connector (`src/main/github-connector-service.ts`, `github-device-flow.ts`, `github-connector-store.ts`)
- GitHub **App** (not an OAuth App) device flow with only the public client ID: `POST https://github.com/login/device/code` (`client_id`) -> `device_code,user_code,verification_uri,expires_in,interval`; poll `POST https://github.com/login/oauth/access_token` with `grant_type=urn:ietf:params:oauth:grant-type:device_code`; honor `interval`, add 5 s on `slow_down`; errors mapped to `denied, expired, device_flow_disabled, client_unknown, refresh_rejected, unreachable, unexpected`. 30 s request timeout; verification URI must be `https://`.
- Tokens expire (GitHub App user-to-server): `access_token` + `refresh_token` (+ `refresh_token_expires_in`); refresh needs **no client secret**. Refresh margin 10 min before expiry; a minute-tick wall-clock check (a single long timer would fire late after sleep); network failures logged once; a rejected refresh sets `expired` but keeps the record so the UI can name the account.
- Store: one encrypted record `{accessToken, accessTokenExpiresAt, refreshToken, refreshTokenExpiresAt, login, userId, avatarUrl, mcpProxy{port,secret}}` in a versioned envelope (64 KB max; an unreadable envelope is reported, never silently dropped), writes serialized by a semaphore, atomic file write. Disconnect opens `https://github.com/settings/connections/applications/<clientId>` so the user revokes.
- Agent access: GitHub's hosted MCP `https://api.githubcopilot.com/mcp/` through a dedicated loopback proxy (token injected, rotated, never exposed), plus injected `GIT_CONFIG_*` entries so `git push` over HTTPS uses the same token. On a joined server the host runs the flow and the client shows `userCode`/`verificationUri` (`connectors-v1`).

### Other connectors (`integrations.md` "Add a connector")
- 1Password (read-only service account token), Bitwarden (`bw` session in memory, or API key + master password), Proton Pass (agent access key). Rules: prefer device code over deep link; register every token for log redaction (`registerSecretValue`) before the first log line; add a privacy note when new data leaves.

### Skills and agent templates (`marketplace/production-catalog/`, `skills-lock.json`, `.agents/skills/`)
- Skill = folder with `SKILL.md` (frontmatter `name`, `description`; body: When to use, Inputs in priority order, Steps, Output). Bundles (`pstack` installs 52 skills). 41 launch skills (build-spec, change-review, bug-triage, pr-follow-up, secure-code-guidance, daily-brief, meeting-actions, ...) and 27 agents; each agent = one job + named result, two input paths, one approval gate, evidence rules, a fixed rubric, adjacent work delegated, optional active routines (installer's timezone; a routine first reads saved setup and calls `routine_no_update` when nothing is new). Agent snapshots pin skill versions; retiring moves a slug to `retired.agents`.
- Skills may call `suggest_marketplace_app` when a needed plugin is missing; when a service is reached in the browser but its plugin is absent, the answer ends with a fixed sentence to install/enable the plugin.
- Skill learning/suggestion/fix loops: `agent/skill-suggestion.ts`, `skill-learning.ts`, `memory-review.ts` (background review on the provider's cheaper default model).

### Gaps vs. SeraBot rules
- Canva, Figma (remote), Linear, Notion, Stripe, Atlassian, GitLab, Sentry, Vercel, Supabase, Neon, Cloudflare, Airtable are remote `http` + OAuth `link` MCP servers: runnable under SeraBot's existing `http` runtime once real hosts replace `*.example.invalid` (owner-approved). The 7 `stdio` entries stay non-runnable per AGENTS.md.
- GitHub is the main missing first-class item: build as a connector (device flow), not a placeholder plugin.

## 6. How to implement in Rust in SeraBot

Constraints (AGENTS.md): per-user envelope-encrypted secrets (`user_secrets.rs`), everything through `gateway`, UID-scoped store methods, invitation-only, secrets write-only and never logged, public repo synthetic, blocklist on outgoing text, approval binds user+args+destination+hash+policy version+expiry, no stdio runner without a new security design, filesystem restricted to inboxes.

### 6.1 Provider accounts (Claude, Antigravity, others)
1. **Schema** (`store.rs`): `provider_accounts(user_id, provider, account_id, label, kind{oauth,api_key}, email, org, created_at, last_used_at, state{ready,signin_needed,limited,disabled}, limited_until, usage_json)`, max 10 per user+provider (mirror `MAX_PROVIDER_ACCOUNTS`). Credentials in `user_secrets` under `provider/<provider>/<account_id>` (refresh token, access token, expiry, meta). API-key accounts use the same table with `kind=api_key`. All methods take the acting `uid`.
2. **No CLI wrapping** (no local process runner allowed): SeraBot speaks the HTTP APIs natively. Borrow from OpenBot: one writer per account refresh (tokio `Mutex` keyed by `(uid, provider, account)`), atomic persist of rotated refresh tokens before using the new access token, and the outcome table: `invalid_grant` -> `signin_needed` (keep registration/metadata, drop tokens), `invalid_client` -> drop registration too, network/5xx/timeout -> no state change.
3. **Claude native sign-in**: authorization-code + PKCE (S256) against Anthropic's consumer OAuth. The authorize/token/refresh URLs, client id and scopes are not defined in OpenBot; take them from the HielCowork reference the owner pointed to and verify against a real owner-approved account before calling it verified. Support the **paste-code** flow (the page shows a code the user pastes back) as the primary method for a server-hosted bot, plus loopback for the desktop console. Multiple accounts per user. Also an **API-key account** (`x-api-key`, `anthropic-version` headers), stored write-only. Importing a local `~/.claude/.credentials.json` (`claudeAiOauth.refreshToken`) is only possible through the desktop console on the owner's machine, never from the server.
4. **Antigravity**: follow the HielCowork implementation (owner instruction). From OpenBot reuse: Google consumer sign-in (`auth_method: consumer`, refresh token + expiry record), quota via `loadCodeAssist` -> `retrieveUserQuotaSummary` on the `cloudcode-pa` / `daily-cloudcode-pa` `v1internal` endpoints (every failure = "no reading"), email from the id token, API-key alternative where a saved key beats a Google account, the classifier categories of section 3, `VALIDATION_REQUIRED` link surfaced as an action button, and keep the provider's best-first model order.
5. **OpenCode/Zen-Go**: key-only account; send the key only to the Go endpoint(s), never to the free tier; "signed in" derived from the model list; free-first ranking; relist shortly after start; usage from the provider usage endpoint. **Hermes/Nous**, **Kimi**, **Muse**, **Cline**, **Grok**: build one generic RFC 8628 `DeviceCodeFlow` (poll `interval`, `slow_down` +5 s, handle `expired`/`denied`) reused by GitHub, Hermes/Nous, Kimi, Muse, Cline, Grok; key accounts for the rest.
6. **Account pool + failover** (`model_router.rs`, `thinking.rs`, `reliability.rs`): port `pickPoolAccount` as a pure function (`PoolCandidate{account_id, windows}`) with the buffer constants above and unit tests; add a `UsageLimitGate` equivalent (`HashMap<(uid,provider,account,model), hold_until>`) and `classify_failure() -> {Billing, ProviderUnavailable, RateLimit, Authentication, Network, Timeout, UsageLimit}`. Pace usage reads like `UsageReadGate` (single flight, 4 min TTL, 5/10/20/40 min up to 1 h backoff, reset on credential change).
7. **Per-bot runtime config**: `bot_runtime { provider, account_id|null(pool), model, thinking_level, backups: Vec<{provider, model, account_id?, thinking?}> (<=8), auto_failover: bool, pending_runtime }`. Fail over only when the turn did no work (`!acted`) and no external effect started: requeue the messages, hold the failed model 10 minutes, write a `model-switch` audit/event row with its cause, return to the original model when the hold ends, clear holds on restart. Thinking level enum `none..ultra` with a per-model supported list + default; clamp to the nearest supported level when the model/provider changes; send nothing when the model is not configurable; keep a legacy mapping for stored values.
8. **Main-bot management tools** (gateway tools, approval-gated): `list_models`, `update_bot_runtime`, `update_bots` (batch, per-bot result), `list_bots` (status, queue length, last activity), `interrupt_bot` (never for user- or routine-started work), `widens_settings` approval when access/privileges grow, a person-request guard (refuse when the request author is a routine, another bot, or tool/model content), and UID checks so a main bot only manages the same user's bots.
9. **Sub-agent auto-resume**: the parent turn records `child_task{id, bot, runtime, acted, status}`; on child failure classified as model/provider error with `!acted`, the orchestrator requeues the child on the next backup (model, then other provider/account), bounded to once per failed model, and emits an event for the sidebar; failures after acting surface to the parent as Blocked with an `Unblock:` line instead of blind replay. Emit bounded subagent step lists (cap N) to the UI, like `turn/subagents/updated`.

### 6.2 Chat view and long, parallel work (`runtime/` and UI)
- Lanes: main chat lane + one lane per side thread; per-bot `task_limit` (default 4, hard cap), server `turn_slots` with priority (human > routine/teammate, oldest first); hold reasons shown in the UI (`task-limit, usage-limit, server-busy, bot-busy, restarting`). A slot never waits on another slot (a teammate request ends the turn; the reply is a new delivery).
- Context: per-turn budget, background summary with a cheaper model at 75% of threshold, provider compaction at 80% of window, stop after 2 ineffective compactions, paginated history tool (24k chars/page). Idempotent operation ids and receipts for retried commands; unknown external-effect outcomes are flagged, never replayed.
- UI: tabs per side thread (open tabs kept per device), activity box with subagent steps, queue panel (edit/steer/delete/reorder with an edit hold), badge/attention logic from the notification model in section 1.

### 6.3 Channels in SeraBot
- New trait `ChannelDriver { receive, post, edit, react, names, history }` in `crates/serabot/src/channels/{slack,discord,telegram,whatsapp}.rs` behind a shared platform-agnostic `ChannelThreads` (link, conversation key, per-conversation execution thread, dedupe key, untrusted-data framing). All sends go through `gateway` (blocklist on outgoing text, approval for the first outbound post to a new destination, audit).
- Per-user scoping: connection rows `(uid, platform, workspace_id)`; one orchestrator bot per user per platform (seeded from `bots/`); tokens in `user_secrets`; invitation-only: link codes (random, hashed, 15 min, bound to uid; Telegram `/start <code>`), allow-lists for Discord roles and WhatsApp senders; unknown senders get nothing except an optional one-time pairing code that the owner confirms.
- Slack: Socket Mode first (no public endpoint) or Events API with signature check; scopes per section 1; status post with Stop button, reactions, thread = conversation, `NO_REPLY` sentinel, auto-join public channels off by default for privacy.
- Discord: Gateway in-process, mention/role-mention only, no privileged intents, reply-chain conversations, 2000-char split, 10 MB cap, Approve/Deny/Stop restricted to the requester.
- Telegram: extend `telegram.rs` with supergroup reply-chain/topic conversation keys, `answerCallbackQuery` buttons, file size caps (20 MB).
- WhatsApp: Meta Cloud API webhook (HMAC verify) first, or defer; port the sender policy and quiet-end rule either way.
- Reliability: backoff 2-30 s with jitter, watchdog on silence, close-code table for linked-device sockets, journal inbound before ack, dedupe set + DB idempotency key, outbound rate limit (>= 1 s per chat).

### 6.4 Marketplace and connectors
- Keep the `/v1/marketplace/*` + `plugin_runtime.rs` model (HTTPS, pinned public IP, egress-listed, approval-gated, tools `plugin.<slug>.<tool>`). Add catalog entries with real hosts only when owner-approved: Canva (`https://mcp.canva.com/mcp`, OAuth `link`), Linear, Notion, Figma (remote), Stripe, Atlassian, Sentry, Vercel, Supabase, Neon, Cloudflare, Airtable. Keep `stdio`/`local` non-runnable and never ask for a secret for a plugin that cannot run.
- Implement **MCP OAuth** in Rust for `link` auth: discovery (RFC 9728 / 8414), dynamic client registration (RFC 7591), PKCE S256, loopback redirect to the desktop console or paste-back, per-user + per-account records (`plugin_account(uid, slug, account_id)`), the outcome table above, RFC 7009 best-effort revoke, SSRF guard (OAuth endpoints must resolve to public IPs, body <=1 MiB, 20 s, DNS pinned per request). Bots never receive tokens: the gateway injects the bearer at call time (the in-process equivalent of `mcp-oauth-proxy.ts`), maps 401 -> one refresh + retry, no sign-in -> typed error (not a 401 to the model).
- **GitHub connector**: new `crates/serabot/src/github_connector.rs` using a SeraBot-owned GitHub App (public client id from config, no secret): device flow endpoints above, refresh 10 min early under a per-user mutex, encrypted record with login/userId/expiries, status endpoint exposing only login/state, disconnect link to the app's connections page. Tools via GitHub's hosted MCP `https://api.githubcopilot.com/mcp/` through the same bearer-injecting gateway path (HTTPS, egress list); write actions (push, merge, issue/PR changes) approval-gated and bound to repo + args; no token in prompts or logs and no local git runner.
- Skills: keep the `SKILL.md` folder format; add a `suggest_marketplace_app` tool so a bot recommends an install instead of improvising; agent templates = one job + named result + approval gate + evidence + rubric; pinned skill versions.
- Privacy/audit: log origin + status only for OAuth failures; register every token with the redactor before first use.
