# Proposal: 0.74.15

Status: **proposed**. Tracks 1 to 6 are the plan agreed after 0.74.14. Track 7 adds the
mail composer, the chat message bar, and message recall and retry. Items marked
**started** already have code on the `release/0.74.15` branch.

0.74.14 added a lot of unverified surface (every release since 0.74.3 still has an open
"owner live pass" line in `tasks/todo.md`). 0.74.15 turns that into verified behaviour,
fixes structural risk, and then adds a smaller set of features.

## Track 1: Verification harness

- Reusable fake IMAP/SMTP server for tests, with Dovecot quirks (untagged lines, `INBOX.`
  delimiters, literals, `APPENDUID`). Replace the per-test copies in `mail.rs` and
  `api/tests/mail_api.rs`.
- Replay corpus of anonymised real server responses (LIST, FETCH, APPEND, SEARCH).
- Headless UI smoke test on the Windows CI leg (open Mail, select, archive, undo).
- One dated owner checklist per release, generated from the open `[ ]` items.

## Track 2: Core harness and stability

- Split the large files with no behaviour change, one PR each: `store.rs` (10.2k lines),
  `mail.rs` (4.2k), `gateway.rs` (3.5k), `turn_loop.rs` (2.3k), `ui_mail.rs` (3.5k).
- One durable job runner (claim, lease, retry, stale recovery) shared by scheduled mail,
  snooze wake, reminders and routines.
- IMAP connection reuse per account and batched header fetches (today every list opens
  a new TLS connection and fetches up to 50 full messages one by one).
- Property tests for the rule "never replay an effect whose outcome is unknown": cancel
  at every await point, crash and resume, assert no duplicate send or write.
- Back-pressure and limits audit: per-user queue depth, provider timeouts, 429 mid-stream.
- A trace id per turn through logs, and a small health view (queue depth, stuck leases).
- Backup restore drill as a CI job.

### Composer (Track 7a, **started**)

- **Footer always visible.** The Send buttons sat at the end of the scrolling body and
  fell out of view in a short window. The footer is now sticky.
- **Recipient chips for To, Cc and Bcc.** Enter, comma, semicolon, Tab, a space after a
  finished address, a paste of several addresses, and leaving the field each turn the
  typed text into a chip and open the next one. Backspace in the empty box removes the
  last chip. Arrow keys pick contact suggestions. Invalid entries are marked and block
  Send with a clear message. Duplicates are ignored.
- **Attach from this PC, drag and drop, or the Library.** Files are uploaded to the
  member's Library and attached by hash, so the server path is unchanged. Limits are
  checked before upload (10 files, 18 MB in total, since the message is base64 encoded
  and capped at 25 MiB). Chips show name and size and can be removed.
- **Ctrl+Enter sends**, Esc closes, wider drawer.
- Later: a From line, signature preview inside the editor, templates, spell check, and
  attachments inside the Undo send hold.

## Track 7b: Recall and retry in the transcript (needs core work)

### What happens today

- **Edit** puts the old text in the composer. Sending it appends a second user message,
  so the transcript shows both.
- **Retry / Regenerate** calls `submit` again, which appends another copy of the same
  user message. After a failed turn the chat shows the message twice.
- The server history is append-only; there is no way to remove or supersede a message.

### Shipped as a stop-gap (**started**)

When two user messages with the same text follow each other with no reply between them,
the transcript shows only the later one (`chat_feed::retry_duplicates`). This hides the
duplicate for the retry case. The server history still holds both, so the model still
sees the message twice. This is cosmetic, not the fix.

### Proposed fix

1. **Retry that reuses the message.** `POST /v1/conversations/{id}/messages/{mid}/retry`
   starts a new turn for the same stored user message. No new row, so the transcript and
   the model context contain it once.
2. **Recall.** `POST /v1/conversations/{id}/messages/{mid}/recall`:
   - Allowed only for the newest user message of the conversation.
   - Stops the turn (the existing stop already cascades to child handoffs) and waits for
     the worker to acknowledge.
   - **Refused (409) if the turn already did anything with an external effect** (a sent
     mail, a posted message, a written file) or left an effect with an unknown outcome.
     The response names what was done so the client can say it.
   - Memory writes made by the turn are listed; recall proceeds only with an explicit
     confirmation, then removes them.
   - In one transaction: cancel pending approvals and queued tasks of the turn, delete the
     user message and every message with that `turn_id` (partial replies, tool results),
     write an audit row, and emit a `message.recalled` event so the desktop and phone
     drop the bubble.
3. **Client.** A Recall button on the newest user message. It removes the bubble, puts
   the text and attachments back in the composer, and shows what was undone. **Edit
   becomes recall plus prefill** when recall is allowed, and falls back to "send as a
   new message" with a note when it is not.
4. **Tests.** Recall at every stage of a turn (queued, streaming, tool running, tool
   finished with and without effects, after reply). Crash between stop and delete.
   Another member can never recall. Duplicate recall is a no-op.

This changes the "append-only history" assumption and the effect-safety rules in the
harness, so it needs your approval before code. It is the headline item of Track 7b.
